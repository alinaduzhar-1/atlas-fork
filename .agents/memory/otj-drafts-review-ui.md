# OTJ drafts review flow

**Decision: the Drafts tab review flow must be IDENTICAL to the Log OTJ flow.** The user explicitly asked for parity; the earlier checkbox + "Confirm and log" button design was removed.
**Why:** One consistent confirmation model across both entry points — reply in chat to confirm.
**How to apply:** The drafts review list shows lavender draft cards, a Total row (only when >1), and the same guidance paragraph as the Log OTJ draft card ("reply to confirm… you're confirming the activities were completed during your working hours"). Confirmation is two-tier like Log OTJ: client regex fast-path (affirmative reply → POST confirm each complete draft) plus a server fallback (client sends `pendingDraftIds`; model answers `[[OTJ_CONFIRMED]]`; server confirms by id and returns `otj_logged`). On confirm, the original review card flips its cards green (message id added to the logged-ids set, passed as a `confirmed` prop, which also freezes its drafts snapshot) and a new "Done — that's logged" message renders summary + follow-up options. Incomplete drafts stay excluded with an "Add details" affordance.

**Correcting a draft from chat ("Add details"):** the `otj-draft-edit` server path returns `editedEntries` alongside `summary`. **Decision (superseding earlier "render only the edited card inline"): a correction must render the FULL drafts review list, not just the single edited card** — the user asked to see ALL drafts (with the edit applied) so they can confirm them all together. Implementation: render exactly ONE live `DraftsReviewList` at the LAST message whose action is `otj_drafts` (computed as `lastDraftsMessageId`); older `otj_drafts` messages render no list. Filter out the now-superseded empty `drafts-review` placeholder message (empty content + no `editedEntries` + not the last drafts msg) so it doesn't leave a blank gap. Because the list reads live query data, the edited entry shows updated automatically. Confirmation still flows through the same conversational path (the correction message keeps its `otj_drafts` action, so it becomes the `pendingDraftsMessage`).
**Edit acknowledgment copy:** the `otj-draft-edit` prose/example/fallback is now just a SHORT ack ("Done — I've updated that draft for you.") with NO review/confirm/working-hours sentence — the review list carries its own confirm-all + "during your working hours" guidance, so putting it in the ack too was redundant. (This intentionally replaced the earlier longer single-card copy.)

**Partial confirm (some drafts incomplete) — ORDER: incomplete block comes AFTER the "Done" message, not inline.** Confirming logs ONLY the complete drafts. The desired post-"Log it" sequence (confirmed via user screenshots) is: (1) confirmed green entries + "Logged: <total>" (the flipped review message — NO incomplete block here anymore), then (2) the "Done — that's logged… Great job! …<weekly>…" `otj_logged` message, then (3) the remaining-incomplete block ("One draft still needs a detail before it can be logged. Add it below and I'll log it too." + incomplete card). **Decision (SUPERSEDES the earlier "render incomplete INLINE inside the confirmed review message" rule):** the confirmed `DraftsReviewList` branch renders ONLY the green cards + Logged total; the incomplete block is rendered by the post-confirm `otj_logged` card instead. **How to apply:** `OtjLoggedCard`, when its message carries `fromDraftsConfirm`/`suppressDraftsNudge`, renders `<PostDraftsConfirmFollowUp>` after the "Great job" line — it reads the live `/api/otj` query and shows `<RemainingDraftsPanel>` (guidance + incomplete cards) when any incomplete drafts remain, else the generic `OtjFollowUpOptions` (nudge suppressed). Both use the LIVE query so the block auto-clears once the missing detail is supplied and logged. Incomplete-draft card = no badge, no button; neutral border, muted title, one warning helper line naming the missing field. The `otj_partial` type is still dead code.

**Completing an incomplete draft from chat (missing-field awareness):** the server prompt annotates every draft in "DRAFT OTJ ENTRIES" with a `missing` array (description/date/duration, computed the same way as the client `getDraftMissingFields`). Rule the model must follow: her reply answers ONLY the fields in `missing`; it must NEVER re-ask for a field already present. When exactly one incomplete draft exists, ANY detail she gives fills that draft — the prompt adds a "RIGHT NOW there is exactly ONE incomplete draft" hint so a reply like "it was yesterday" resolves to the date and emits `otj-draft-edit` immediately instead of asking her to restate task/duration.
**Why:** without the `missing` annotation the model asked for task+duration it already had when the user only supplied the date.

**"Waiting for your review" nudge: count ALL drafts, suppress by CONTEXT not by completeness.** The `OtjFollowUpOptions` after-drafts nudge ("You have N drafts waiting for your review…") must count ALL draft-status entries (complete + incomplete) — before review the learner expects the full count (e.g. 3), so counting complete-only was wrong. The redundancy problem (nudge reappearing after a partial confirm when only the incomplete draft is left, already shown inline) is fixed by a `suppressDraftsNudge` prop threaded from the message, NOT by changing the count. **Why:** the distinction that matters is *before-review* (show full count) vs *post-drafts-confirm* (suppress) — not complete vs incomplete. **How to apply:** the post-confirm "Done — that's logged" `otj_logged` message carries `fromDraftsConfirm: true` in its action data (set in BOTH the client fast-path append AND the server-response append when `pendingDraftsMessage` exists); the render passes it as `suppressDraftsNudge` to `OtjLoggedCard`→`OtjFollowUpOptions`. A regular chat OTJ-log confirm does NOT set the flag, so its nudge still fires if seed drafts remain.

**Figma → Stardust token mapping for the lavender entry card:**
- lavender fill `#f5f7ff` → `bg-action-secondary-hover`
- blue accent border/title `#4a5ff7` → `border-secondary` / `text-action`
- divider `#dbdad6` → `border-tertiary`
- Buttons have no `fullWidth` prop — use `className="w-full"`. `TextInput` supports `hideLabel` + `fullWidth`.

**Confirm rendering must be timing-immune + both paths must mirror each other:** the green "logged" snapshot in the confirmed review list must come from a snapshot FROZEN onto the review message's action (`confirmedSnapshot`, captured from the OLD query data BEFORE `setQueryData`), NOT from the live query. Relying on the live-query `useEffect` snapshot caused the green cards to vanish (heading, no cards) because `setQueryData` (which removes confirmed drafts) could re-run the snapshot effect while `confirmed` was still false, wiping the complete drafts.
**Why:** React state (`loggedOtjMessageIds` → `confirmed` prop) and React Query cache updates are not batched together, so the "confirmed" flag can lag the summary change — a race.
**How to apply:** BOTH confirm paths (client affirmative-regex fast-path AND the server `[[OTJ_CONFIRMED]]` → `otj_logged` path) must (1) freeze `confirmedSnapshot` on the review message, and (2) detect remaining incomplete drafts and append an `otj_partial` message (never the `otj_logged` celebration) when any remain. The server always returns `otj_logged`; the client overrides the appended message's action to `otj_partial` when incomplete drafts survive. The affirmative regex rejects phrasings with commas (e.g. "great, log it") so those fall through to the server path — that path used to skip partial handling entirely, dropping the incomplete card.
